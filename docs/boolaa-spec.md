# Boolaa product spec (native iOS + web)

Boolaa is a private, invite-only social app built around **bubbles**: small groups (2–150 people, default 12) of flatmates, friends or clubs. Everything a user sees is scoped to the **current bubble**, which they switch between in the header.

Both clients (`apps/boolaa-ios` SwiftUI, `apps/boolaa-web` Next.js) talk directly to Supabase. The backend contract is `supabase/migrations/*.sql`: tables, RLS policies and RPCs. Clients never bypass RLS. Membership changes only go through RPCs. The legacy React Native app in `apps/boolaa` is a visual and behavioural reference only, and its schema mistakes (`profiles` vs `users`, `desc` vs `description`) are fixed in the migration.

## Backend contract summary

| Table | Columns clients use | Writes |
|---|---|---|
| `users` | id, name, avatar | update own row (name, avatar) |
| `bubbles` | id, name, description, logo, max_size, invite_code, created_by | via `create_bubble`; whoever `can_manage_bubble(id)` (the owner and admins) may update name, description and logo; no other column is writable by clients. `created_by` is history only, not ownership |
| `bubble_members` | user_id, bubble_id, approved, role (`owner`/`admin`/`member`, see Roles) | delete own row = leave bubble; no client INSERT/UPDATE (roles change only through RPCs) |
| `join_requests` | id, user_id, bubble_id, approver_ids[] | via `request_to_join` / `approve_join_request` / `reject_join_request`; requester may delete own (cancel) |
| `chat_messages` | id, bubble_id, sender_id, content, image_path, deleted_at, created_at | insert own (text and/or photo); delete own via `delete_chat_message`; read pages via `chat_messages_page`; realtime INSERT + UPDATE filtered by `bubble_id=eq.<id>` (see Chat) |
| `chat_reads` | user_id, bubble_id, last_read_at | own rows only, written by `mark_chat_read`; counts via `chat_unread_counts()` |
| `events` | id, bubble_id, creator_id, title, description, datetime, location, rsvp_list[] | CRUD own; RSVP via `toggle_rsvp(p_event_id)` |
| `food_posts` | id, bubble_id, user_id, image, description | CRUD own |
| `market_items` | id, bubble_id, owner_id, image, title, description, status (`free`/`trade`), availability (`available`/`reserved`/`taken`) | CRUD own; UPDATE limited to image, title, description, status, availability (see Marketplace availability) |
| `shared_links` | id, bubble_id, user_id, url, title, tags[], preview_status, preview_title, preview_description, preview_site_name, preview_image_path | CRUD own (url, title, tags); preview_* are server-written (see Link previews) |
| `reactions` | id, bubble_id, user_id, reaction, target_type, target_id | via `toggle_reaction` only (see Reactions) |

The RPCs, called with named params:
- `create_bubble(p_name, p_description, p_max_size)` returns the bubble row, and the caller becomes its owner.
- `request_to_join(p_invite_code)` returns the join_request row. It raises `invalid invite code`, `already a member`, `bubble is full` or `too many attempts` (see Invite links). The code is normalised (upper-case, letters and digits only), so `flat-2026` works.
- `get_invite_preview(p_code)` and `rotate_invite_code(p_bubble_id)`: see Invite links.
- `approve_join_request(p_request_id)` returns a bool: true when the requester was admitted. A requester is admitted when approvals from **current** members exceed half the approved members **and** there is a free seat. If the bubble is full, the approval is kept and the requester is admitted automatically when a seat frees up. It never raises `bubble is full`.
- `remove_member(p_bubble_id, p_user_id)`: the owner removes anyone else, an admin removes plain members only. It raises `only the owner can remove members` (caller is a plain member; text kept for compatibility), `only the owner can remove admins`, `use leave to remove yourself` or `member not found`.
- `transfer_ownership(p_bubble_id, p_new_owner)` and `set_member_role(p_bubble_id, p_user_id, p_role)`: see Roles.
- **When a member leaves or is removed**, the database cleans up automatically:
  - If the owner left (or was removed by moderation, or deleted their account), ownership passes to the longest-standing **admin**, else the longest-standing member.
  - A bubble with no members left is deleted.
  - The departed member's votes are removed.
  - Queued requests that now have a majority are admitted.
- **Realtime tables**: `chat_messages`, `join_requests` and `bubble_members`. Pending screens and Settings should subscribe to them instead of polling. `bubbles` too (`20261123130000_bubble_cover.sql`): clients listen to UPDATE on `bubbles` (no filter, RLS decides) while signed in and merge name, description and logo into their bubble list by id; the pending screen reloads.
- **Live feeds** (migration `20261123110000_realtime_feeds.sql`): `events` (RSVPs arrive as an UPDATE of the event's `rsvp_list`), `food_posts`, `market_items` and `shared_links` are in `supabase_realtime` too. The Events, Food, Marketplace and Links screens subscribe while shown, on one channel per screen named `<table>:<bubble id>`:
  - INSERT and UPDATE with the filter `bubble_id=eq.<current bubble>`. Realtime checks them against the subscriber's SELECT policies, so blocked authors, other bubbles and unverified sessions (`require_verified_session`) get nothing.
  - DELETE unfiltered (Realtime can't filter deletes and, with RLS on, sends only the primary key): remove the row by id and ignore ids the list doesn't hold. The tables keep the default replica identity.
  - A new id is fetched once with its author join (RLS decides again). An UPDATE of a row in the list is merged in place, keeping the joined author. Merges are by id, so the echo of the client's own write changes nothing, and lists keep their sort order (events by `datetime`, the rest newest first).
  - Once the subscription is live the screen reloads once, to catch changes made while connecting. Subscriptions end when the screen goes away, the bubble changes or the user signs out.
- **Push notifications** (`docs/push-notifications.md`): clients call `register_push_token(...)` after the device check and on every start, and `unregister_push_token(p_token)` before signing out. They read and update their own `notification_prefs` row (master switch, per type, `preview_content`) and `bubble_mutes` rows. Pushes carry `{type, bubble_id, target_id}` for deep links. UI (all three clients): **Notifications** screen (web: a section in Settings; iOS: Profile → Notifications; Android: Settings → Notifications) with this device's permission state, the master switch, seven per-type switches and message previews (its hint quotes the current bubble's name, "New message in <bubble>", or "Boolaa" without a bubble); **Mute this bubble** in bubble Settings; a dismissible "Turn on notifications" card on Home until the OS/browser has been asked. The OS prompt only follows a tap. A tapped push switches bubble, opens the screen and highlights the event/post/item for 4 s.
- `reject_join_request(p_request_id)` takes the request id and returns nothing.
- `toggle_rsvp(p_event_id)` returns the new `rsvp_list`. Since `20261123220000_past_events_export_check.sql` it raises `event has ended` (→ `eventEnded`, "This event has already ended.") for an event whose start + 1 hour has passed (`event_has_ended(datetime)`; events have no end time and last 1 hour, as in "Add to calendar"), both to RSVP and to un-RSVP.
- `search_bubble(p_bubble_id, p_query, p_limit, p_kinds)` and `chat_messages_around(p_bubble_id, p_message_id)`: see Search.

Embedding author info: `select('*, author:users!<fk_column>(id, name, avatar)')`, e.g. `sender:users!sender_id(...)`, `creator:users!creator_id(...)`, `owner:users!owner_id(...)`, `user:users!user_id(...)`.

Storage: **every photo bucket is private** (`avatars`, `food.images`, `market.images`, `bubble.images`, `link.previews`, `chat.images`; see "Private photos"). Object path **must** be `<auth uid>/<uuid>.<ext>` (enforced by policy). Rows store the object's public-form URL (`…/storage/v1/object/public/<bucket>/<path>`) as its identifier; clients never load it, they show a signed URL. The exception is `bubble.images`, whose paths are `<bubble id>/<uuid>.jpg` (see "Bubble photo"). `chat.images` stores the object path (not a URL) in `chat_messages.image_path` (see Chat), and `link.previews` the path in `shared_links.preview_image_path`.

### Images
Every client runs a picked photo through the same pipeline before upload (web `src/lib/image.ts`, iOS and Android `ImageCompression`):
- **Decode, then make upright**: apply the EXIF orientation to the pixels (web `createImageBitmap(..., {imageOrientation: "from-image"})`, iOS ImageIO thumbnail with transform, Android `ExifInterface` + matrix).
- **Downsize**: long edge at most **1600 px** (avatars **512 px**), aspect ratio kept, never upscaled. Rounding is `round(side * maxSide / longEdge)`, so all clients produce the same size (e.g. 4032x3024 → 1600x1200; the shared fixture `exif-gps.jpg` → 1067x1600, avatar 341x512).
- **Re-encode as JPEG, quality 0.82**, on a white background (transparent PNG areas don't turn black). Upload as `<uid>/<uuid>.jpg` with `content-type: image/jpeg`. WebP is not used: Safari's canvas can't encode it.
- **No metadata**: only pixels reach the encoder, so EXIF, GPS location, camera, XMP and IPTC from the source are gone. iOS and Android also drop any APP1–APP15/COM segment the encoder writes itself (ImageIO adds a small Exif and Photoshop block). Each platform's tests check the uploaded bytes for this.
- **Limits** (`20261123100000_image_limits.sql`, checked by Storage on upload only, so older objects keep loading): `avatars` and `bubble.images` 2 MB (512 px), `food.images` and `market.images` 5 MB; MIME types `image/jpeg` and `image/webp` only. Clients refuse inputs above 50 MB before decoding.
- **Errors** (glossary, "Image upload errors"): too large (client check, or Storage `statusCode` 413 / `EntityTooLarge`) → `imageTooLarge`; undecodable file, or Storage 415 / `invalid_mime_type` → `imageUnsupported`. Storage answers both with HTTP 400 locally and 413/415 hosted.
- **Thumbnails**: none. Supabase image transformations are a paid feature, and a `_thumb` variant would double the uploads and the deletion paths (replace, delete, account deletion, moderation cleanup). Lists show the same image, sized by CSS / native views and loaded lazily; a 1600 px JPEG is a few hundred KB.

### Private photos (migration `20261123210000_private_photos.sql`)
- **Why**: before, anyone holding a photo URL could open it without an account. Now Storage serves an object only to a signed-in, verified caller the policies allow; the old `/object/public/...` URL answers 400 and anon reads nothing.
- **Who reads** (`can_read_image(bucket, name)`, plus the existing owner, manager and moderation policies):
  - `avatars`: the owner, anyone `shares_bubble_with()` the owner (the same rule as reading the `users` row: a shared approved bubble, or a join request to a bubble the caller is in, so voters see the requester), and admins.
  - `food.images` / `market.images`: an approved member of the post's bubble with no block either way with the author (the row's own rule), while a post / item by the folder's owner references the object. Admins: photos of reported posts / items.
  - `bubble.images`: approved members of the bubble. A non-member reads only the bubble's **current** cover, and only with a join request to it (pending screen) or after opening a valid invite preview in the last hour (below).
  - `link.previews`: approved members of the link's bubble (folder = link id), no block with the poster, while the link references the object.
  - `chat.images`: unchanged (see Chat).
  Deleting the referencing row (or replacing the photo) cuts access at once; a signed URL already handed out works until it expires.
- **Invite preview**: `get_invite_preview` records `(caller, bubble)` in `invite_preview_grants` (no client access) when a non-member opens a valid code; that lets the caller sign the current cover for an hour. No Edge Function and no public bucket: the invite screens sign `logo` like any other photo. Codes stay throttled.
- **Clients** (one helper each: web `src/lib/storage-url.ts` `useSignedUrl`, iOS `PhotoURLs` + `StoredImage`, Android `PhotoUrls` + Coil `PhotoUrlInterceptor`): every stored URL of ours is turned into a **signed URL (1 hour)**; requests made together (a list appearing) are signed with one `createSignedUrls` call per bucket; signed URLs are cached **per storage path** and reused until 5 minutes before they expire (Android also keys Coil's memory and disk cache by `<bucket>/<path>`), so refreshes don't re-download; a failed load drops the cached URL and signs once more. Unreadable photos show the usual fallback (initials, orb, placeholder). External URLs (seed photos) pass through.
- **Unchanged**: object paths, upload / delete policies, MIME and size limits, the sweeps (`sweep_bubble_images`, `sweep_link_preview_images`, service role), moderation cleanup and the `link-preview` function (service role). Existing objects keep working: nothing moves, only the read path changed. Data export signs every photo for 7 days. Landing and Open Graph images never use member photos.

### Bubble photo (`20261123130000_bubble_cover.sql`)
- **Column**: `bubbles.logo`, the public-form URL naming the photo, or null (shown through a signed URL, see "Private photos"). A trigger refuses anything but an existing object in `bubble.images/<this bubble id>/` (`invalid bubble logo`, shown as the generic error).
- **Who edits**: `can_manage_bubble(p_bubble_id)`: the approved owner and admins (see Roles); the row policy and the storage policies all call it.
- **Storage**: private bucket `bubble.images`, path `<bubble id>/<uuid>.jpg`. The folder is the bubble, not the uploader, so a new owner (after the owner leaves or deletes their account) can replace or remove the old file, and account deletion doesn't break the bubble's photo. Managers may upload, update, list and delete in that folder; members (and invitees, see "Private photos") read it through signed URLs.
- **Pipeline**: the avatar settings (long edge 512 px, JPEG 0.82, no metadata, 2 MB). No crop: every client shows it in a circle (cover/fill). A square photo looks best, as the hint says.
- **Flow**: upload, then `update bubbles set logo = <url>`, then delete the previous object (best effort). If the row update fails, delete the new upload. Remove: set `logo = null`, then delete the object.
- **Cleanup**: anything clients miss (failed deletes, abandoned uploads, and the photo of a bubble that was deleted because its last member left, deleted their account or was banned) is an orphan. pg_cron runs `sweep_bubble_images()` hourly; it asks the Storage API (through pg_net) to delete up to 100 orphans older than an hour. It needs the Vault secrets `storage_sweep_url` (project URL) and `storage_sweep_key` (service role key) and does nothing without them. Bubble photos can't be reported yet.
- **Display**: the photo, or a fallback on the bubble's own colour (derived from its id): initials in large places, the coloured orb in the switcher chip. Shown in the header switcher chips, Settings (large, with the owner's controls) and the pending-approval list.
- **Strings** (all clients): `bubblePhoto` "Bubble photo", `addBubblePhoto` "Add a photo", `changeBubblePhoto` "Change photo", `removeBubblePhoto` "Remove photo", `bubblePhotoHint` "Everyone in the bubble sees it. Square photos look best.", `bubblePhotoOf` "Photo of {name}" (accessibility label).

### Invite links (migration `20261123140000_invite_links.sql`)
- **Link**: `https://boolaa.ro/join/<CODE>`, where CODE is the bubble's `invite_code`. Typed code, link and QR code are one secret: one thing to share, one thing to revoke. A link never bypasses approval: it opens a preview, and joining is `request_to_join` plus the members' majority vote, as with a typed code.
- **Codes**: new bubbles and rotated codes get 10 characters from `23456789ABCDEFGHJKMNPQRSTUVWXYZ` (no 0/O, 1/I/L; about 49 bits). Older 8-character codes keep working until rotated. No expiry: rotation is the revocation, and approval gates every join anyway.
- **Who**: every member sees, copies and shares the code, link and QR code. Only the **owner and admins** rotate it (`rotate_invite_code(p_bubble_id)` returns the new code; a plain member gets `only the owner can change the invite code`, text kept for compatibility), because rotation kills every link in circulation, including other members' invites. Clients can't change `invite_code` with an UPDATE (column grant, plus a trigger).
- **Preview**: `get_invite_preview(p_code)` returns no row (unknown code) or one row `{bubble_id, name, logo, member_count, max_size, status}`. `status` is `member` (then `bubble_id` is set, to switch to it), `pending` (the caller already asked), `full` or `open`; for non-members `bubble_id` is null. Nothing else (description, members, content) is shown. Signed-in, verified sessions only (not anon), so link previews in chat apps and signed-out web visitors see a generic "You've got an invite".
- **Throttle**: each preview of an unknown code is logged per user (`invite_lookup_failures`, no client access). After 20 in an hour, both the preview and `request_to_join` raise `too many attempts` (errors `tooManyInviteAttempts`; `onlyOwnerCanRotate` for the rotation error).
- **Web** `/join/CODE` (open path in the proxy): signed out → sign in / create account with `?next=/join/CODE` (also through Google/Apple and the device gate), plus a `boolaa_invite` cookie that sends a new user from onboarding back to the invite after email confirmation; App Store / Android download buttons (`APP_STORE_URL` / `ANDROID_URL` in `src/lib/site.ts`, "Coming soon" while null). Signed in → preview and "Request to join", "already asked" with a link to the pending list, or "Open bubble".
- **App links**: `/.well-known/apple-app-site-association` (applinks `/join/*` for `W5WKF2N472.ro.boolaa.app`) and `/.well-known/assetlinks.json` (`ro.boolaa.app`, SHA-256 of the release certificate), served as JSON by route handlers and skipped by the proxy matcher (`src/lib/app-links.ts`). iOS: Associated Domains `applinks:boolaa.ro`; Android: `autoVerify` intent filter for `https://boolaa.ro/join/*`. Both apps also accept `boolaa://join/CODE` and `ro.boolaa.app://join/CODE`, keep the code through sign-in, device gate and onboarding, then show the same preview. Without the app, the link opens the web page.
- **QR code**: shown in Settings on iOS (CoreImage) and Android; it encodes the link, so the system camera opens the app or the web page. No in-app scanner.

Local dev: `supabase start` serves the API at `http://127.0.0.1:55321`. `supabase status -o env` prints `ANON_KEY` / `PUBLISHABLE_KEY`. The seeded logins are `alice@boolaa.test`, `bob@boolaa.test` and `carol@boolaa.test`, all with password `password123`. Alice and Bob share the "Flatmates" bubble (invite `FLAT2026`) and "Climbing Crew" (invite `CLIMB123`). Carol has a pending request for Flatmates.

### Roles (migration `20261123190000_bubble_roles.sql`)

- **Model**: `bubble_members.role` is `owner` (exactly one per bubble: a partial unique index forbids two), `admin` (0..n) or `member`. Ownership was already this column; `bubbles.created_by` only records who created the bubble. Clients can't INSERT or UPDATE `bubble_members`; roles change only through the RPCs below.
- **Permissions** (the UI hides what a role can't do; the server enforces it anyway):

  | Action | Owner | Admin | Member |
  |---|---|---|---|
  | Edit name, description, photo (`can_manage_bubble`) | yes | yes | no |
  | Rotate the invite code | yes | yes | no |
  | Remove a plain member | yes | yes | no |
  | Remove an admin | yes | no | no |
  | Make admin / remove admin (`set_member_role`) | yes | no | no |
  | Transfer ownership (`transfer_ownership`) | yes | no | no |
  | Approve / reject join requests | one vote | one vote | one vote |
  | Leave | yes (hand-over) | yes | yes |

  Approval stays a strict majority of members: admins don't bypass the vote.
- `set_member_role(p_bubble_id, p_user_id, p_role)`: owner only; `p_role` is `admin` or `member`; target is another approved member. Raises `only the owner can change roles`, `invalid role`, `use transfer_ownership` (on yourself) or `member not found`.
- `transfer_ownership(p_bubble_id, p_new_owner)`: owner only; target must be an approved member (not a pending requester). The old owner becomes an **admin**: they usually still help run the bubble, a mistaken transfer doesn't strip them of everything, and the new owner can demote them in one tap. Both rows are locked and updated in one transaction (no moment with zero or two owners). Raises `only the owner can transfer ownership`, `already the owner` or `member not found`.
- **Hand-over** (`after_member_removed`): when the owner leaves, is removed by moderation or deletes their account, the longest-standing admin becomes owner, else the longest-standing member. Empty bubbles are deleted, departed votes stripped, queued requests admitted, as before.
- **Errors**: `only the owner can remove admins`, `only the owner can transfer ownership` and `only the owner can change roles` map to one message ("Only the owner can do that.", web `errors.ownerOnlyAction`, iOS `.ownerOnlyAction`, Android `error_owner_only_action`); the others to the generic error.
- **Live**: role changes are UPDATEs of `bubble_members` (already in realtime). Settings reloads its members list on them; the user's own membership watch updates their role in the bubble list.
- **UI** (all three clients, Settings → Members): Owner (crown) and Admin (shield) badges; an owner-only per-member menu with Make admin / Remove admin / Transfer ownership; a confirmation before a transfer naming the new owner and saying you'll lose owner rights; notices "{name} is now an admin." / "… is no longer an admin." / "… is now the owner.". Strings: glossary "Roles".

### Chat (migration `20261123120000_chat_improvements.sql`)
- **Pages**: `rpc('chat_messages_page', {p_bubble_id, p_before_id, p_limit: 50}).select('*, sender:users!sender_id(id, name, avatar)')` returns a page **newest first** (reverse it for display). `p_before_id = null` gives the newest page; for older ones pass the id of the oldest message loaded. The keyset is `(created_at, id)` on the server, so clients never send timestamps (Swift `Date` would drop the microseconds and skip messages). A page shorter than 50 means the start of the chat is reached. Load the next page when the list is scrolled to (near) the top, and keep the scroll position anchored on the message that was first before the page arrived. The server sets `created_at` on insert, so messages can't be backdated.
- **Live**: one channel `chat:<bubble id>` with INSERT **and** UPDATE, both filtered by `bubble_id=eq.<id>`. Merge by id: an INSERT adds a message, an UPDATE replaces it in place (this is how deletions arrive). Realtime runs the SELECT policies on both, so blocked senders, other bubbles and unverified sessions get nothing.
- **Delete your own message** (only yours: context menu / long press, with a confirmation): `rpc('delete_chat_message', {p_message_id})` returns `{id, image_path}`. If `image_path` is set, remove that object from `chat.images` (best effort). Show the message as a placeholder ("This message was deleted", no report menu) right away; everyone else gets the UPDATE live.
  - **Soft delete, not hard delete.** The row stays with `deleted_at` set and its text and `image_path` wiped (a check constraint enforces both). Why: members see it vanish live through an RLS-checked UPDATE (a DELETE event carries only the primary key and skips RLS); the placeholder keeps replies around it understandable; paging cursors and unread markers never point at a missing row; and moderation keeps the row, its author and its place in the conversation (`admin_get_report` context).
  - **Report evidence**: if the message has an **open** report, its text and photo path are first copied into `chat_message_evidence` (no client access) and the photo object is kept, so deleting can't destroy evidence. The admin view shows it as "deleted by its author". When the report is resolved (any action), the photo is named for removal like a `delete_content` photo, and the evidence row is dropped once no report on the message is open. Admin **Delete content** still hard-deletes the row (and its photo).
  - Clients can no longer delete (`chat_delete_own` dropped) or update chat rows directly.
- **Photos**: a photo button in the composer. The picked image goes through the image pipeline ("Images", 1600 px, JPEG 0.82, no metadata) and is uploaded to `chat.images` at `<uid>/<uuid>.jpg`; then the message is inserted with `image_path` and the composer text as an optional caption (`content` may be empty when there is a photo). If the insert fails, remove the uploaded object. The insert policy checks that the photo is in the sender's own folder and already uploaded, and `image_path` is unique (one message per photo).
  - **Private bucket**: `chat.images` is not public (5 MB, JPEG/WebP). A member can read a photo only while a live message they can see references it: same bubble, no block either way, verified session. Deleting the message revokes access at once, even if the object removal fails. Clients show photos through **signed URLs** (`createSignedUrl(s)`, 1 hour, cached per path; batch per page where the SDK allows). Public URLs don't work. Since `20261123210000_private_photos.sql` every other photo bucket is private too (see "Private photos").
  - Photos are removed on message deletion (above), on account deletion (the `<uid>/` folder of `chat.images` with the other buckets) and by moderation (`admin_resolve_report` names `chat.images` + path; the admin view removes it).
- **Unread counts**: `rpc('chat_unread_counts')` returns one row per approved bubble: `bubble_id`, `unread_count` (messages from others after the marker, not deleted, blocked senders excluded, **capped at 100**: show "99+" above 99) and `last_read_at`. Without a `chat_reads` row the marker is the time the user joined. Show a badge on each bubble chip in the switcher and on the chat button (current bubble). Refresh on start / foreground, when the bubble list changes, after marking read, and (debounced) on any `chat_messages` INSERT or UPDATE (a deleted unread message leaves the count) from someone else, on a second channel `unread:<user id>` with no filter (RLS limits it to the user's bubbles).
- **Last-read marker**: `rpc('mark_chat_read', {p_bubble_id, p_message_id})` with the newest message shown; the marker never moves back. Call it when the chat opens and as new messages arrive, only while the chat is actually visible (app in the foreground / tab visible).
- **"New messages" divider**: when the chat opens, keep that bubble's `last_read_at` from before marking read and draw the divider above the first message from someone else that is newer than it and not deleted (as the server counts). It stays until the chat is closed.
- **Home** shows the latest messages that aren't deleted; a photo without a caption shows the "Photo" label.
- **Push**: a photo without a caption is pushed as "📷 Photo" (localized); a message deleted before the push is sent is skipped.
- **Links** (all clients): `http://`, `https://` and bare `www.` URLs in message text are tappable and open outside Boolaa (web: new tab, `rel="noopener noreferrer nofollow"`; iOS: `Text` with `.link` runs → `openURL`; Android: `LinkAnnotation.Url`). Same rules everywhere (`src/lib/linkify.ts`, `Linkify.swift`, `Linkify.kt`): a link starts on a word boundary and runs to whitespace, trailing `. , ! ? ; : ' "` and unbalanced closing brackets stay text, `www.` gets `https://`, only http(s) with a host. Long URLs still wrap. **No previews in chat.**
- **Bubble switch while the chat is open** (e.g. a tapped push for another bubble): the chat reloads and lands at the newest message, like a fresh open; it never keeps the old scroll offset or pages in older messages on its own (iOS keys the scroll view by bubble and arms older-page loading only after the first page settled).
- **Header**: the chat (and Links) header shows the bubble's cover photo like the switcher chip, else its colour dot.
- **Web photos** go through the shared `useSignedUrl` helper (`src/lib/storage-url.ts`): batched, re-signed before the hour ends, signed once more after a failed load.
- Errors: `message not found` → `chatMessageGone` (glossary).

### Marketplace availability (migration `20261123170000_market_status_calendar.sql`)
- **Two independent fields**: `status` says what kind of offer it is (`free` / `trade`, badge top-left); `availability` says whether it can still be had: `available` (default, no badge), `reserved` (tangerine badge, hourglass) or `taken` (dark badge, photo dimmed and greyed). Clients read unknown or missing values as `available`.
- **Who it's reserved for is not stored.** The deal is arranged in the bubble chat and the owner knows who it's for. A "reserved for X" label would publish members' private arrangements to the whole bubble (including people X has blocked) and would need consent, block and account-deletion handling for little gain. Others can still ask about a reserved item (to be next in line).
- **Only the owner changes it**, with a plain `update({availability})` on the row (`market_update_own` + the verified-session gate; no RPC). Non-owners' updates match no row. Column-level grant: clients may UPDATE only `image, title, description, status, availability` (so an item can no longer be moved to another bubble, re-owned or backdated). Owner UI: a "Mark as" picker on the item (web `<select>`, iOS/Android menu) and a 3-way picker in the edit form. The list updates optimistically; members get the UPDATE live (Live feeds).
- **List order and filter**: taken items sink to the bottom, the rest stay newest first (sorted at render time, so a live change moves the card). A "Hide taken" chip next to All/Free/Trade hides them (off by default, not saved).
- **"Ask in chat"** (the "message the owner" shortcut): Boolaa has one group chat per bubble and no direct messages, so the button opens the bubble chat with the composer prefilled, **not sent**: `@<owner name>, is “<title>” still available?` (glossary). The user can edit it or not send it. Shown only on other members' items that aren't taken; never on your own. If the owner's name is unknown, the "someone" fallback is used. Web passes the draft through sessionStorage + a window event (the chat route may already be mounted); iOS and Android through their shell router.

### Add to calendar (events)
- Events have `datetime` (the start, timestamptz), an optional `location` and `description`; there is **no end time and no all-day flag**. Every client exports a **1-hour** event; no schema change.
- **Web**: the calendar button on each event card downloads `<title>.ics` (`src/lib/ics.ts`, RFC 5545): `VCALENDAR` with `VERSION:2.0`, `PRODID`, `METHOD:PUBLISH` and one `VEVENT` with `UID:<event id>@boolaa.ro` (stable, so re-importing updates instead of duplicating), `DTSTAMP` (export time, UTC), `DTSTART`/`DTEND` in UTC (`…Z`, exact for timestamptz, no VTIMEZONE needed), `SUMMARY`, and `DESCRIPTION` / `LOCATION` when set. TEXT is escaped (`\\ \; \, \n`), lines are folded at 75 octets without splitting UTF-8 characters, every line ends in CRLF. The generator also supports all-day (`VALUE=DATE`, exclusive end, date in a given zone) and explicit end times for later use.
- **iOS**: EventKit `EKEventEditViewController` prefilled (title, start, start + 1 h, location, notes), so the user picks the calendar and confirms. From iOS 17 it runs without calendar access; `NSCalendarsWriteOnlyAccessUsageDescription` (and the legacy key) are set in `project.yml` and localized in `InfoPlist.xcstrings`.
- **Android**: `Intent.ACTION_INSERT` on `CalendarContract.Events.CONTENT_URI` with begin/end (+1 h), title, description and location: the calendar app shows its own confirm screen, no permission. Without a calendar app a "No calendar app found." message is shown.
- No subscribable per-bubble feed (it would need token-authenticated public URLs).

### Link previews (same migration; Edge Function `link-preview`)
- **What**: when a link is shared (Links), the server fetches the page's Open Graph title, description, site name and image and stores them with the link, so every client shows the same card. URLs inside chat messages get no preview (not in scope).
- **Columns** on `shared_links`: `preview_status` (`none` / `pending` / `fetching` / `ready` / `failed`), `preview_title` (≤ 200), `preview_description` (≤ 300), `preview_site_name` (≤ 80), `preview_image_path` (object path in the private bucket `link.previews`, or null), `preview_fetched_at`. Only the server writes them: on a client insert, or an update that changes `url`, a trigger clears them and sets `pending`; other edits keep them. Links that existed before the migration stay `none` (plain).
- **Flow**: an AFTER INSERT / UPDATE OF url trigger asks the `link-preview` Edge Function to fetch it (pg_net, fire-and-forget, Vault `link_preview_url` and optional `link_preview_secret`; like the report alerts). The function claims the row (`claim_link_preview`: pending → fetching, so each URL is fetched once and a request with a link id can't make it fetch anything else), builds the preview and stores it (`store_link_preview`) only if the URL hasn't changed meanwhile. The UPDATE reaches clients through the Links live feed. Throttle: 30 previews per user per hour; later links stay plain (`none`). A lost call is re-queued every 10 minutes (`retry_link_previews`, pg_cron); after a day the link is marked `failed`. Why a trigger and not a client call: every client gets it for free, nothing depends on the client being alive, and the URL fetched is always the one stored.
- **SSRF guard** (`supabase/functions/link-preview/guard.ts`, unit-tested in `supabase/tests/link_preview_unit.test.ts`): only `http`/`https` on the default ports 80/443, no credentials in the URL, no single-label or local names (`localhost`, `*.local`, `*.internal`, …). The host must resolve (A and AAAA) only to public unicast addresses: private, loopback, link-local and metadata (169.254.169.254, fd00:ec2::254), CGNAT, multicast, reserved and documentation ranges, IPv4-mapped/NAT64/6to4/Teredo forms of those are refused. Redirects are followed by hand, at most 3, each hop re-checked. Timeouts 8 s for the page, 6 s for the image. Only `text/html` / `application/xhtml+xml` is parsed, reading at most 512 KB (the head is enough). Text is entity-decoded, stripped of tags, control and bidi characters, single-lined and cut to length. Residual risk: fetch resolves DNS again (rebinding); hosted Edge Functions can't reach the project's private network, and nothing fetched is ever returned raw.
- **Images, privacy**: clients never load the third-party image (that would leak every member's IP address to the site, and Boolaa promises no tracking). The function downloads the `og:image` through the same guard (≤ 3 MB, raster by magic bytes only, no SVG; dimensions read from the header before decoding, ≤ 16 MP, ≥ 48 px), re-encodes it as a metadata-free JPEG (long edge ≤ 1200 px, quality 82, on white) and uploads it to the private bucket `link.previews` at `<link id>/<uuid>.jpg` (1 MB, JPEG only, service role only). Clients show it through a signed URL (see "Private photos"); members of the link's bubble only. If the image fails, the preview is text-only. Orphans (deleted links, changed URLs, stale results) are swept hourly by `sweep_link_preview_images()` (pg_cron, same Vault secrets as the bubble-photo sweep).
- **Clients**: a link with `preview_status = 'ready'` shows a card under the user's title and tags: image (if any, 1.91:1, cover), preview title (2 lines), description (2 lines, if any), and the domain (host without `www.`) with the site name. Tapping opens the URL as before. `pending` / `fetching` shows the plain link with a small "Loading preview…" line; `none` / `failed` shows the plain link. The image is decorative for screen readers (the title is read). String `linkPreviewLoading` (web `links.previewLoading`): Loading preview… / Se încarcă previzualizarea… / Chargement de l'aperçu… / Cargando vista previa… / Caricamento dell'anteprima….
- **Production**: deploy the function (`supabase functions deploy link-preview`, `verify_jwt = false`), set `LINK_PREVIEW_SECRET` and store the same value plus the function URL in Vault (`link_preview_secret`, `link_preview_url`). Without `link_preview_url`, links stay plain.

### Data export (GDPR right of access; migration `20261123200000_data_export.sql`, Edge Function `data-export`)
- **What**: "Download my data" in the profile / account settings of all three clients (web: profile sheet, above Delete account; iOS and Android: profile sheet, between Sign out and Delete account). It gives one JSON file, `boolaa-data-YYYY-MM-DD.json`, with everything Boolaa stores about the user (Art. 15 access, Art. 20 portability).
- **Flow**: explanation → `device-code` `{action:"send", purpose:"sensitive_action", sensitive_action:"export_data"}` (email "confirm: download a copy of your data") → 6-digit code → verify → `POST /functions/v1/data-export` (body `{}`, user JWT, `functions.invoke` or fetch for the raw bytes) **in the same session within 10 minutes** → save the file (web: download; iOS: `.fileExporter` to Files; Android: SAF `ACTION_CREATE_DOCUMENT`). If the user cancels the save dialog in an app, the bytes are kept with a Save button until the sheet closes, because of the hourly limit.
- **Server**: `export_my_data()` (security definer, `auth.uid()` only) checks a device-checked session (not age or suspension: the right of access doesn't depend on them), a `sensitive_action` code verified **in this session in the last 10 minutes**, always (not behind `device_verification_enforced`), and the limit of **one export per user per rolling hour** (`data_export_requests`, no client access; refused calls aren't counted). The function calls it with the user's JWT, then adds a **7-day signed URL** for every photo in `avatars` / `food.images` / `market.images` / `chat.images` (all private; only paths in the user's own `<uid>/` folder are ever signed), orders the keys for reading and adds an `about` block.
- **Contents**: profile and account status; consent (age, terms version); Auth account (email, pending email change, sign-in providers, user metadata, timestamps, ban), sign-in identities, active sessions (IP, user agent, no ids or tokens), the account's Auth audit-log entries (90 days, 500 max); trusted devices (label, dates, 8-character hint of the hash), emailed-code log (purpose, times, attempts; no code or hash), password-reset grants; memberships (bubble name and photo, role, joined), own join requests (approvals as a count), approvals given (request and bubble ids), chat read markers; every chat message written (soft-deleted ones as metadata only: their text and photo were wiped), own events (RSVPs as a count plus "you are going"), RSVPs to others' events (title only while the user can still see the event: approved member, no block either way), food posts, market items, shared links, reactions given (target type and id), reports filed (with status, without the moderator's note), blocks made; notification preferences, mutes, notifications queued (type and delivery only), push tokens (last 4 characters; web: the push service host; no keys); invite-code failures; whether the user is a moderator; previous export times; every file in the user's folder of the per-user buckets (orphans included).
- **Left out, and why** (also listed in the file's `not_included`): other members' messages, posts, names and photos, and anything from bubbles the user isn't in; **who blocked the user** and **reports other people filed about the user**, because they hold the reporters' identity and words and moderation promises never to reveal a reporter (GDPR Art. 15(4): the copy must not adversely affect others; the account status in the file shows any action taken; the moderation records about a user are given on request to privacy@boolaa.ro with other people's details removed, see `docs/moderation.md`); the evidence copy of a message kept for an open report and moderators' notes; password hashes, tokens, codes and their hashes, raw device ids and push keys; bubble photos (they belong to the bubble) and link-preview images (made by the server).
- **Why JSON + signed URLs, not a ZIP**: hosted Edge Functions get about 2 s of CPU and 256 MB per request. A heavy user's photos (up to 5 MB each, possibly hundreds) won't fit, and a background job would have to keep a second full copy of the user's data in Storage (another thing to secure, expire and delete). The JSON is small, readable and machine-readable, and the links cover the photos for 7 days.
- **Limit up front** (migration `20261123220000_past_events_export_check.sql`): `rpc('data_export_available_at')` returns when the next export is allowed (null = now). Clients ask when the export sheet opens and again before sending the code; while limited they show "You can download your data once an hour. Try again after HH:MM." (locale time; web `errors.exportRateLimitedUntil`, Android `error_export_rate_limited_until`, iOS English key) and disable "Send code". The `device-code` send step also refuses `sensitive_action: "export_data"` while limited: 429 `{error: "export_rate_limited", retry_after, available_at}`, no email sent. The function's 429 below stays as the backstop.
- **Errors** (`{"error": ...}`): 401 `unauthorized` (refresh and retry once), 403 `session_not_verified`, 403 `reauthentication_required` (back to "Send code"), 429 `export_rate_limited` + `retry_after` seconds and a `Retry-After` header (`exportRateLimited`; clients show the timed message), 500 `server_error` (generic). RPC texts: `reauthentication required`, `session not verified`, `export rate limited` (DETAIL = seconds).
- **Strings** (web `profile.export*`, `errors.exportRateLimited`; Android `profile_export_*`, `error_export_rate_limited`; iOS English keys): see `docs/i18n-glossary.md`, "Data export and theme".
- **Tests**: `supabase/tests/data_export.test.ts` (the function's handler runs in-process: the local runtime only loads functions registered when the stack started), web `tests/data-export-theme.spec.ts`, iOS `DataExportTests`, Android `DataExportTest`.

### Search (migration `20261123180000_bubble_search.sql`)
- **What**: one search box per bubble over chat messages (text), events (title, description, location), food posts (description), market items (title, description) and shared links (title, URL, tags, preview title and description). Results are typed and best first.
- **RPC** `rpc('search_bubble', {p_bubble_id, p_query, p_limit: 30})` (optional `p_kinds` text[] filters by kind) returns rows `{kind, id, title, snippet, author_id, author_name, created_at, event_at, rank, matched_words}`. `kind` uses the reaction/report target names (`chat_message`, `event`, `food_post`, `market_item`, `shared_link`); clients skip kinds they don't know. `title` is null for chat messages and food posts (show the author instead); links fall back to the preview title, then the URL. `snippet` is plain text (≤ 160 characters, "…" where cut) around the first hit. `event_at` is the event's date. `matched_words` are the folded query words to highlight. Limit 1–50 (default 30).
- **Visibility is RLS's**: the function is `SECURITY INVOKER` and reads the tables as the caller, so membership, blocks (both ways), the verified-session gate and inactive accounts apply exactly as for the screens; nothing is re-implemented. Soft-deleted messages have no text and are skipped. Non-members, other bubbles and `anon` get nothing.
- **Matching**: the query is folded with `lower(unaccent())` (immutable wrapper `search_fold`), so case and diacritics never matter in any language (`sarmalute` finds "Sărmăluțe", cedilla ş/ţ and comma ș/ț both fold to s/t, `creme` finds "crème", œ → oe). Fewer than 2 characters (after trimming) returns nothing; input is cut at 100 characters. A row matches when **every word** (letters and digits only, max 8) starts a word of the row: full text, `simple` config (no stemming or stop words, the same for all 5 languages), prefix terms; **or** the whole query (3+ characters) occurs anywhere: trigram-indexed `LIKE` with `%`, `_` and `\` escaped (fragments like `zza` → "pizza", URL pieces). User input is never spliced into SQL: words are reduced to `[[:alnum:]]` before forming the tsquery and the pattern is a bound value.
- **Ranking**: whole query in the title, then anywhere in the row, then `ts_rank`, then newest. Each type contributes at most `p_limit` before the overall cut.
- **Indexes**: per table a GIN full-text index on `to_tsvector('simple', search_doc(...))` and a GIN `gin_trgm_ops` index on `search_doc(...)` (chat: partial, `deleted_at is null`). Small bubbles are served by the existing `bubble_id` indexes; the GIN indexes keep large tables fast.
- **Highlighting**: clients fold each character the same way (NFD, drop combining marks, lower-case, œ/æ/ß/ø/ł/đ/ı expanded), map folded positions back to the original text and mark every occurrence of every matched word in title and snippet. Web renders text nodes and `<mark>` (never HTML); iOS an `AttributedString`; Android an `AnnotatedString`.
- **Opening a result** (search closes first): events, food posts and market items open their tab and reuse the push deep-link highlight (scroll + brand ring for 4 s); links open Links with the same highlight (new on all clients). Web uses `/events?event=`, `/food?post=`, `/marketplace?item=`, `/links?link=`, `/chat?message=` plus an in-page event when that route is already mounted.
- **Jump to a chat message**: `rpc('chat_messages_around', {p_bubble_id, p_message_id}).select('*, sender:users!sender_id(...)')` returns, newest first like `chat_messages_page`, up to 25 messages older than the target, the target and everything after it up to the newest (capped at 1000 rows from the newest end). It is contiguous with the newest page, so clients merge it by id: live messages and "load older" keep working. Fewer than 25 rows older than the target means the start of the chat. Then scroll the message to the centre and ring it for 4 s. No rows (no access, deleted, unknown) or the target missing (more than 1000 newer messages) → "We couldn't find that message in the chat." and the chat stays at the bottom.
- **UI** (all three clients): a search button (magnifier, "Search this bubble") in the shell header next to the avatar; web opens a dialog, iOS a sheet, Android a full screen. Input is debounced 300 ms and only the latest query's answer is shown. States: hint (empty), "Type at least 2 characters.", spinner, "No results for “…”" with a hint, error with "Try again". Rows: round icon in the feature colour, title (or author), up to 2 lines of snippet, then kind · author · relative date (events: the event date). The result count is announced to screen readers. Changing bubble clears the search.

### Safety and account (App Store guidelines 1.2 and 5.1.1(v))
- **Block**: `insert into blocks (blocker_id = me, blocked_id)`, and unblock by deleting your own row. `select` returns only the user's own block list.
  - Blocking is two-way and enforced by RLS: neither side sees the other's chat, events, food, market items or links, live updates included.
  - Members lists still show blocked people, so you can unblock them.
- **Report**: `report_content(p_target_type, p_target_id, p_reason, p_details)`.
  - Target types: `user`, `chat_message`, `event`, `food_post`, `market_item`, `shared_link`.
  - Reasons: `spam`, `harassment`, `hate`, `sexual`, `violence`, `self_harm`, `other`.
  - The server works out the author and bubble. Errors: `cannot report yourself`, `report target not found`.
  - Reports go to a moderation queue that only admins (`public.admins`, through the admin RPCs) and the service role can read. Each report emails moderation@boolaa.ro with a link to `/admin`.
  - After reporting, offer "Also block <name>?".
- **Delete account**: `delete_my_account()`. First list and remove every object under `<uid>/` in `avatars`, `food.images`, `market.images` and `chat.images`, ignoring failures (not `bubble.images`: a bubble's photo belongs to the bubble and stays with its next owner). Then call the RPC and sign out locally.
  - The deletion cascades to the user's profile, memberships and all their content. Owned bubbles pass to the next member, and bubbles left empty are deleted.
  - The UI must warn clearly that this can't be undone and ask for a confirmation step.
- **Suspended or banned accounts** (`users.status`: `active` / `suspended` / `banned`, plus `status_reason`, `status_until`, `status_changed_at`). Moderators set them from the web admin view (`/admin`, see `docs/moderation.md`).
  - An inactive account (banned, or suspended with `status_until` null or in the future) reads nothing and can't post or call RPCs (`account suspended`). It can still read its own `users` row and call `delete_my_account()`. A suspension ends by itself at `status_until`.
  - Sign-in and token refresh fail with the Auth error code `user_banned` while it lasts.
  - Every client shows a **suspended screen** instead of the app: title, "You can use Boolaa again from <date>" (suspended), the reason (report-reason labels), an appeal link to privacy@boolaa.ro, and sign out. On `user_banned` at sign-in, show it without date or reason. Texts: `suspended.*` in the web's `messages/*.json`.
  - Their posts stay visible to their bubbles; a ban also removes them from every bubble.

## Screens and flows

1. **Auth**: login (email and password) and register (name, email, password), with the name passed as sign-up metadata `{ name }`. Register requires the **"I'm 16 or older"** checkbox and links to Terms and Privacy: Boolaa is rated **16+**. Sign out lives in the profile sheet.
2. **Routing gate**: signed out goes to Auth. Signed in with 0 approved bubbles goes to Onboarding. Otherwise the user lands in Main.
3. **Onboarding**:
   - **Create a bubble**: name, description, max size.
   - **Join a bubble**: invite code, or an invite link (`/join/CODE`, see Invite links).
   - **Pending approval**: the user's pending requests, each showing its bubble name and approvals so far, with a cancel button. Refreshes periodically or on pull.
4. **Main shell**:
   - **Header**: large screen title, avatar button (opens the profile sheet), and a horizontal bubble-switcher chip row with a "+ New" chip that opens create or join.
   - **Tabs**: Home, Events, Food Circle, Marketplace, Settings.
   - **Chat**: a floating chat button on every tab.
5. **Home**: a combined, recency-sorted feed for the current bubble: latest chat messages, food posts, market items, upcoming events and links. Each card deep-links to its section.
6. **Chat**: messages in chronological order with sender avatar and name. Your own messages are aligned right. Realtime inserts, auto-scroll to the newest message, composer at the bottom. Details in "Chat" below.
7. **Events**: "My events" and "Bubble events" sections sorted by date. Create, edit and delete your own events (title, description, date and time, location). RSVP toggle with a count. "Add to calendar" on every event (see "Add to calendar"). Other members' events and RSVPs update live. **Past events** (start + 1 h has passed; re-checked every 30 s while the screen is open) leave both sections and go to a **"Past events (N)" section at the bottom, collapsed** by default, most recent first, dimmed, with "Ended" instead of the RSVP button and "N people went" instead of "N going"; the creator can still edit or delete them.
8. **Food Circle**: "My posts" and "From the bubble" sections. Create and edit (photo upload, description) and delete your own. Other members' posts appear, change and disappear live.
9. **Marketplace**: grid of items with a Free/Trade badge, a Reserved/Taken badge and filter chips (All/Free/Trade, plus "Hide taken"); taken items sink to the bottom. Create, edit and delete your own (photo, title, description, status, availability); "Mark as" on your own items, "Ask in chat" on others' (see "Marketplace availability"). Updates live.
10. **Links** (opened from Home and Settings): add a URL with a title and comma-separated tags, filter by tag, open the link, delete your own. Updates live.
11. **Settings** (for the current bubble):
    - Bubble photo, name and description, which the owner and admins can edit (photo: add, change, remove).
    - **Invite code** with copy and share buttons, and the **invite link** with copy link, share link and QR code (apps); the owner and admins can replace the code ("New code", with a confirmation).
    - **Members** list with Owner and Admin badges. The owner gets Make admin / Remove admin / Transfer ownership per member (transfer asks for confirmation: you lose owner rights and become an admin); the owner removes anyone, admins remove plain members (see Roles).
    - **Pending join requests**: requester, approvals so far versus members needed, and approve and reject buttons. Hide approve if you already approved.
    - **Leave bubble** with a confirmation step.
12. **Profile sheet**: avatar (upload or replace), editable name, email (read-only), sign out, "Download my data" (see Data export), Delete account.

## Visual language

The full design system (colour, typography, layout, motion, components, voice) is in `docs/design-system.md`. In short:

- **Colours**: brand purple "grape" `#7357F6` (evolved from `#9D78BD` / `#7B61FF`) with a joyful secondary palette (coral, mint, sky, sunny, pink, tangerine, indigo). Each bubble gets its own colour, derived from its id; each feature has its own colour (chat grape, events coral, food tangerine, marketplace mint, links sky). Light background `#FBF8FF`, dark background `#15111F` with dark cards `#221C33`.
- **Navigation**: a floating dock: a rounded "pill" tab bar with circular icon buttons (the active one is filled with the tab's colour and slides between tabs) and, beside it, the round chat button, a glossy purple 60pt bubble.
- **Shapes**: glossy bubbles, pills and rounded cards (24pt radius) with soft purple-tinted shadows. Avatars are circles; users without a photo get initials on their own colour.
- **Motion**: springy and quick, with still fallbacks under Reduce Motion.
